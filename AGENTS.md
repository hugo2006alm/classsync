# ClassSync repository guide

This file is the authoritative guide for coding agents working in this repository. Read `CONTEXT.md`, `README.md`, relevant files under `docs/`, and accepted ADRs before changing architecture or integration behavior.

## Product contract

ClassSync is a local-first university manager whose v1 turns completed Fireflies transcripts into structured Gemini study summaries in the correct Notion subject with near-zero interaction. Windows is the primary unattended processor. Android is a portable processor, status view, and review surface. The Cloudflare relay is a fast coordination path; direct Fireflies polling remains recovery.

Preserve these invariants:

- Notion is canonical for subjects and published summaries. Fireflies is canonical for transcripts.
- Only subjects with `Status = In progress` are classification candidates. Never hardcode a semester or subject list.
- One `SyncCoordinator.run(reason)` pipeline serves every trigger. Platform code may trigger it but must not duplicate business logic.
- Persist queue state before external side effects. Every processing state must recover after process death.
- A Fireflies transcript must produce at most one Notion summary across retries and devices.
- Keep API credentials in OS secure storage. Never place credentials in SQLite, logs, diagnostics, source, or CI output.
- Keep full transcripts, prompts, summaries, and Notion content off the relay. D1 may store coordination metadata only.
- Notion schema changes are additive and require explicit setup confirmation. Never silently rename or remove user properties.
- Regeneration and republishing must preserve user-authored Notion content.
- Healthy automation stays quiet. Reviews and actionable failures identify the exact job.
- Future academic modules belong behind clean feature/domain boundaries. Do not add placeholder screens.

## Repository map

```text
apps/client/                  Flutter app shared by desktop and mobile
  lib/app/                    bootstrap, routing, shell, theme
  lib/core/                   DB, HTTP integrations, security, notifications
  lib/domain/                 academic and sync rules
  lib/features/               Overview, Classes, Sync, Setup, Settings
  lib/platform/               desktop and mobile adapters
  test/                       unit and mocked pipeline tests
apps/relay/                   Cloudflare Worker, D1 migrations, Vitest tests
docs/                         architecture, integrations, operations, ADRs
packaging/windows/            Inno Setup definition

```

Dependency direction: features use domain contracts; integration and platform adapters implement external behavior; domain code must remain free of Flutter widgets and platform plugins.

## Development commands

From repository root:

```powershell
pnpm install --frozen-lockfile
pnpm relay:check
```

From `apps/client`:

```powershell
flutter pub get
dart run build_runner build
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
flutter build windows --release
flutter build apk --debug
```

Run platform builds when tooling exists. Windows plugin builds require Windows Developer Mode for symlinks. Never weaken tests or CI to work around a local machine limitation.

## Generated and environment-owned files

- `lib/core/database/classsync_database.g.dart` is generated from Drift tables. Regenerate after schema edits and commit source plus generated output together.
- `lib/firebase_options.dart` and `android/app/google-services.json` are generated by FlutterFire. Change them only as part of an explicit Firebase configuration task.
- `apps/relay/wrangler.jsonc` contains deployable resource identifiers but no secrets. Store Worker secrets with Wrangler secret bindings.
- Android keystores, `key.properties`, `.dev.vars`, credentials, and exported diagnostics never belong in Git.

Firebase and GitHub repository settings may be configured outside this worktree. Inspect current files before editing them; avoid overwriting concurrent changes. Do not deploy, rotate secrets, create releases, or mutate Notion schema unless the task explicitly requests it.

## Database and queue changes

Treat queue code as crash-recovery code. A state transition needs:

1. persisted precondition and ownership/lease;
2. idempotent external operation or durable remote checkpoint;
3. persisted completion;
4. startup recovery for interrupted states;
5. tests for failure before and after each side effect.

Increase `schemaVersion` for schema changes. Add ordered migrations and tests that open the previous schema, migrate it, and verify retained data. Do not hand-edit generated Drift code.

## Integration rules

- Use official current Fireflies, Gemini, Notion, Cloudflare, Firebase, Flutter, and Android documentation when changing contracts.
- Bound pagination, payload sizes, transcript chunks, retries, and concurrency.
- Distinguish retryable transport/rate-limit failures from authentication, permissions, schema, and validation failures.
- Honor both delta-seconds and HTTP-date forms of `Retry-After`.
- Treat transcript text and remote metadata as untrusted input. Delimit model data from instructions and validate all model output against local candidate IDs and domain rules.
- Validate outbound URLs and require HTTPS for integration endpoints.
- Redact secrets before persistence, UI display, notifications, or telemetry.

## Testing expectations

Add the smallest meaningful test at the owning boundary:

- domain: classification policy, chunking, retries, state transitions;
- database: uniqueness, leases, recovery, migrations, cleanup;
- HTTP adapters: pagination, malformed responses, status mapping, retry headers;
- pipeline: crash/retry checkpoints, low-confidence review, duplicate devices;
- relay: real Worker runtime with D1 migrations, auth, replay, rate limits, per-device delivery;
- UI/platform: setup validation, notification preference, lifecycle triggers, deep links, background scheduling.

CI must use mocks or emulators and must never require production credentials.
