## Scope and conclusion

This audit reviewed the initial product specification, repository README and docs, Flutter client, Drift schema, Fireflies/Gemini/Notion adapters, Cloudflare Worker and D1 migrations, Firebase push path, tests, packaging, and GitHub Actions present in the local worktree.

The architecture is coherent for an early prototype: one shared pipeline, clear local/cloud ownership, minimal relay data, secure-storage abstraction, structured Gemini output, and a focused university UI. It is not production-ready yet. Main blockers are crash recovery, process/device concurrency, global idempotency, destructive Notion replacement, Android execution reliability, and thin real-boundary test coverage.

No critical issue was found. Nine high-risk issues can lose work, duplicate summaries, destroy user content, or break zero-click processing. Security posture is reasonable for a prototype but relay identity, API-key transport, replay/resource controls, local data protection, and release signing need hardening.

Audit snapshot was volatile: Firebase and GitHub configuration were being changed concurrently. During review, Drift generated code and its notification-field wrapper were updated by that work. Findings below describe the final inspected local snapshot. No Firebase Console, Cloudflare dashboard, Notion workspace, Fireflies account, Gemini project, GitHub repository settings, or branch-protection state was mutated or assumed.

Observed strengths worth preserving:

- clear local-first data ownership and one shared coordinator;
- OS secure-storage abstraction and targeted secret redaction;
- parameterized D1 queries, HMAC verification, constant-time bearer comparison, and event uniqueness;
- structured Gemini schemas plus local subject-ID validation;
- Fireflies overlap polling, local job uniqueness, retry metadata, and persisted Notion page IDs;
- focused current UI with no fake future modules;
- mocked happy-path, review, retry, duplicate, chunking, mapping, and policy tests.

## High-risk findings

### H-01 — Interrupted processing states never recover

**Evidence:** `SyncCoordinator` writes `fetching_transcript`, `classifying`, `summarizing`, and `publishing` before work (`apps/client/lib/domain/sync/sync_coordinator.dart:282`, `:310`, `:354`, `:401`). `readRunnableJobs` selects only `discovered`, `queued`, and `failed_retryable` (`apps/client/lib/core/database/classsync_database.dart:298`).

**Failure:** app/OS death after a processing status is persisted leaves the job permanently displayed as processing. Restart, polling, and manual Sync never claim it again. This contradicts durable-queue and reboot acceptance criteria.

**Fix:** add `lease_owner`, `lease_expires_at`, and stage checkpoint semantics. Claim runnable or stale-processing jobs in one SQLite transaction using compare-and-set. On startup, reclaim expired leases and resume from persisted transcript/classification/summary/page checkpoints. Do not reset every interrupted job blindly; publishing must resume the same remote page.

**Tests:** kill/reopen simulation at every stage; stale lease recovery; active lease exclusion; recovery after Notion page creation and after append response loss.

### H-02 — Multiple isolates/processes can process one local job simultaneously

**Evidence:** foreground UI serializes only through one `SyncController`, while WorkManager and Firebase background handlers instantiate and run their own coordinators (`apps/client/lib/platform/mobile/background_sync.dart:16`, `apps/client/lib/platform/mobile/firebase_push_service.dart:21`). `_processJob` has no transactional claim or ownership check.

**Failure:** foreground Sync, periodic work, and FCM wake-up can read the same runnable row and perform duplicate Gemini calls or overlapping Notion mutation. Two Windows processes can do the same because launch-at-startup has no single-instance lock.

**Fix:** use the database lease from H-01, renew it during long work, reject overlapping claims, and add a Windows single-instance mutex. Make notification/deep-link launches activate the existing process. Keep side effects idempotent even with a lease.

**Tests:** two coordinators against one SQLite file; lease expiry; duplicate FCM + foreground trigger; two-process Windows smoke test.

### H-03 — `Fireflies ID` check-then-create is not global idempotency

**Evidence:** client queries Notion, then separately creates a page (`apps/client/lib/domain/sync/sync_coordinator.dart:408`, `:435`). Notion does not enforce uniqueness on rich-text properties. ADR-003 calls this global idempotency, which overstates the guarantee.

**Failure:** desktop and Android can both observe no matching page and create one. Both local databases then hold different Notion page IDs. Duplicate acceptance criterion fails.

**Fix:** move coordination, not content, into relay D1. Add a unique row keyed by Fireflies ID with atomic claim/lease, processing device, expiry, final Notion page ID, and completion status. Device acquires claim before Gemini/Notion work; retries resume or take over expired claims. Keep Notion preflight lookup as reconciliation. Update ADR-003 or replace it with a claim protocol ADR.

**Tests:** concurrent claims from two devices; lease expiry/takeover; response loss after page create; reconciliation when Notion page exists but relay completion did not persist.

### H-04 — Regeneration deletes every top-level Notion block

**Evidence:** `replaceSummaryPage` fetches all child IDs and deletes each before rebuilding (`apps/client/lib/core/integrations/notion/notion_client.dart:225`). UI promises only that the existing page is updated.

**Failure:** any student edits, annotations, embeds, or content created by a Notion template are deleted. A mid-operation failure can leave the study page empty or partial.

**Fix:** place generated content under a clearly marked ClassSync-owned container or between durable marker blocks. Persist owned block IDs/content revision. Replace only owned blocks, preserve user blocks, and construct the replacement before retiring the previous generated section when the API permits. Warn explicitly if legacy pages cannot distinguish ownership.

**Tests:** page with user blocks before/after generated section; template blocks; failure during replacement; repeated regeneration.

### H-05 — Discovery outages stop already-durable queue work

**Evidence:** `run` performs Fireflies listing, saves cursor, and refreshes Notion subjects before reading runnable jobs (`apps/client/lib/domain/sync/sync_coordinator.dart:119`, `:136`, `:138`, `:140`). Fireflies errors and subject-refresh errors escape the run.

**Failure:** Fireflies outage prevents processing manual imports and already-fetched transcripts. Notion subject refresh failure prevents use of a valid local cache. One integration becomes a wider pipeline outage.

**Fix:** split run into independently reported phases: relay discovery, Fireflies recovery discovery, optional/staleness-based subject refresh, and durable queue processing. Catch per-source retryable discovery errors, retain health state, and continue any job whose required checkpoints/cache exist. Advance each cursor only after its own discovery succeeds.

**Tests:** Fireflies down with manual job; relay down with polling success; Notion refresh down with cached subjects; both discovery paths down with runnable persisted job.

### H-06 — Notion renderer silently truncates structured content

**Evidence:** `_text` truncates every value to 2,000 UTF-16 code units (`apps/client/lib/core/integrations/notion/notion_client.dart:469`). Paragraphs and code are split first, but bullets and callouts pass full examples, exam hints, uncertainties, conclusions, and key points directly (`:437`, `:445`). Titles and metadata also truncate without validation.

**Failure:** long model fields lose content silently. Truncation may split a surrogate pair. Study notes can omit the end of an example, uncertainty, or conclusion without diagnostics.

**Fix:** centralize Unicode-safe rich-text chunking. For paragraph-like blocks, use multiple rich-text objects within API limits; for list/callout blocks, emit continuation blocks when total limits are exceeded. Validate title and metadata lengths separately and record any intentional normalization. Never use substring as silent loss control.

**Tests:** 2,001+ character bullets/callouts, emoji at boundary, long title, exact round-trip block text.

### H-07 — Notion child-count checkpoint can skip or mis-associate content

**Evidence:** `ensureSummaryContent` treats total top-level child count as the offset into newly generated blocks (`apps/client/lib/core/integrations/notion/notion_client.dart:261`). Existing pages found by Fireflies ID are also passed to this method.

**Failure:** a default template, user edit, or earlier generated layout with a different block sequence makes count unrelated to desired offset. ClassSync may skip initial sections, append mismatched tails, or declare a corrupted page complete.

**Fix:** persist a generated-content revision/hash and explicit per-chunk markers or owned block IDs. Reconcile marker sequence, not total child count. If ownership cannot be proven, stop for review instead of guessing. Combine with H-04 ownership boundaries.

**Tests:** template-created page, inserted user block, changed summary layout between retries, partial previous revision, response loss after committed chunk.

### H-08 — Android push callback runs an unbounded full pipeline

**Evidence:** Firebase background handler initializes every integration and awaits the complete coordinator (`apps/client/lib/platform/mobile/firebase_push_service.dart:21-43`). Long transcript summarization may make many sequential Gemini calls. No foreground-service promotion exists; `docs/background-processing.md` says long foreground processing must display a notification but implementation does not provide it.

**Failure:** Android may terminate background execution mid-job. H-01 then strands the job. Delivery behavior differs across Android versions and notification/data states, so zero-click automation is unreliable.

**Fix:** background FCM handler should validate/persist minimal event data and enqueue unique WorkManager work quickly. Worker claims jobs and checkpoints each stage. Promote user-initiated or long processing to a compliant foreground service with visible progress; otherwise pause and resume safely. Add lifecycle/resume recovery.

**Tests:** background time-budget cancellation, process death, duplicate push, notification permission denied, WorkManager retry, foreground promotion.

### H-09 — Long-transcript AI work has no cost/context bound

**Evidence:** chunking uses a 48,000-character heuristic, summarizes every chunk sequentially, then JSON-encodes all detailed partials into one final prompt (`apps/client/lib/core/integrations/gemini/gemini_client.dart:105-145`). Manual import has no input limit. Classification sampling caps sentence count but not characters.

**Failure:** very long recordings can create large API cost, exceed model context/output limits, time out Android background work, or make final synthesis fail after all prior calls succeeded.

**Fix:** estimate tokens, cap per-job input and chunk count, expose cost/work estimates for exceptional imports, set output-token limits, persist each partial, and use bounded hierarchical synthesis batches. Bound classification sample by tokens/characters as well as sentence count. Resume completed chunks after failure.

**Tests:** maximum supported lecture, oversized manual import, one huge sentence, synthesis with many partials, retry after chunk N without repeating earlier chunks.

## Medium-risk findings

### M-01 — Relay identity and acknowledgement are global

One shared `DEVICE_API_TOKEN` authorizes every device, and one `acknowledged_at` hides an event globally (`apps/relay/src/security.ts:33`, `apps/relay/src/index.ts:122-145`). A lost device can list/ack all events and register or unregister any known push token; the first device to acknowledge removes the relay fast path for others.

**Fix:** issue random per-device credentials; store only hashes; attach device identity and scopes; add revoke/rotate flow; track delivery/ack per device. Couple processing ownership to H-03 claim leases.

### M-02 — Webhook replay and resource controls are incomplete

Webhook timestamp is type-checked but never checked for freshness (`apps/relay/src/index.ts:14`). Body and IDs have no small application limit. Endpoints have no rate limiting. Database uniqueness limits duplicate effects while a row exists, but it is not replay validation or abuse control.

**Fix:** reject timestamps outside a documented skew window, cap body/ID sizes before expensive work, store a bounded replay key, and configure Worker rate limits for webhook/device endpoints. Test old/future timestamps, oversized bodies, repeated auth failures, and burst traffic.

### M-03 — Gemini API key is placed in URL query data

`GeminiClient` sends `?key=...` (`apps/client/lib/core/integrations/gemini/gemini_client.dart:175`). URLs are more likely than headers to appear in proxies, crash reports, or transport diagnostics.

**Fix:** send `x-goog-api-key` header as shown in current official Gemini examples. Add a request-inspection test proving no credential exists in URI or logged error text.

### M-04 — Notification preference does not gate local notifications

UI persists `notificationsEnabled`, but `SyncCoordinator` always calls the notifier and `ClassSyncNotificationService` always calls `show` (`apps/client/lib/core/notifications/classsync_notification_service.dart:58`, `:80`, `:100`). Preference currently controls FCM token registration only.

**Fix:** inject a preference-aware notifier or gate each notification at dispatch. Define whether disabling notifications suppresses success, review, failure, and foreground-service notifications separately; OS-required foreground notification cannot be disabled.

### M-05 — Relay setup verifies public health, not supplied credentials

Setup and Settings call unauthenticated `/health` without the entered token (`apps/client/lib/features/setup/setup_wizard.dart:424`, `apps/client/lib/features/settings/settings_screen.dart:702`). Any healthy Worker URL plus wrong token is saved as connected.

**Fix:** add authenticated `GET /session` or call `GET /events?limit=1` with token. Verify expected relay protocol/version and surface 401 distinctly.

### M-06 — Setup does not validate Notion schemas before completion

Wizard tests `/users/me`, lists data sources, and accepts two IDs. It does not verify required property names/types, relation target, permissions, active-subject query, or summary-page write capability before marking setup complete.

**Fix:** implement read-only schema validation first; show per-property mapping; perform a non-destructive capability check; add metadata only after explicit confirmation. Never create a visible test summary silently.

### M-07 — “Learn from corrections” exists only as an unused table

`ClassificationCorrections` is declared but no DAO, write after manual selection, classifier hint lookup, inspection UI, or test exists. Manual correction therefore teaches nothing despite docs claiming corrections as local state.

**Fix:** store deterministic hints on confirmation, show/delete them in Settings, and pass bounded inspectable hints to classification. Add conflict-resolution and false-positive tests.

### M-08 — App-resume and manual-import execution are incomplete

`SyncReason.appResume` exists but no lifecycle observer invokes it. Manual import persists a queued job and navigates to detail, but does not start processing; user must wait for periodic work or press Sync now elsewhere.

**Fix:** add `AppLifecycleListener`/`WidgetsBindingObserver` with debouncing and automatic-sync policy. After manual import, invoke the shared coordinator for that queued job or expose an immediate “Process” action.

### M-09 — Settings invariants rely on debug assertions and nullable fields cannot be cleared

Threshold ordering is asserted inside `ClassificationPolicy`; asserts disappear in release. Independent sliders can set review threshold above auto-publish threshold. `AppSettings.copyWith` uses `value ?? old`, so Notion IDs and relay URL cannot be explicitly set to null.

**Fix:** validate settings at persistence boundary, constrain paired sliders, return actionable errors, and use a sentinel/nullable wrapper or dedicated clear methods. Add release-mode domain tests.

### M-10 — Retry classification is too coarse

`Retry-After` parses only integer seconds (`apps/client/lib/core/integrations/integration_exception.dart:26`). Fireflies marks nearly every non-auth GraphQL error retryable (`apps/client/lib/core/integrations/fireflies/fireflies_client.dart:146`). Not-found, invalid query, plan/permission, and malformed response cases can retry pointlessly.

**Fix:** parse both standard `Retry-After` forms, inspect structured provider codes, distinguish not-ready from terminal not-found/schema/plan errors, and preserve safe provider request IDs for diagnostics.

### M-11 — Relay push failures are swallowed

`notifyDevices` awaits `Promise.allSettled` but does not inspect rejected results (`apps/relay/src/firebase.ts:102`). Webhook returns accepted and no retry/alert records transient FCM failures.

**Fix:** inspect results, remove terminal invalid tokens, record bounded delivery attempts/status, retry transient failures through a queue/alarm, and emit redacted metrics. Polling remains recovery but should not hide push health.

### M-12 — Relay data has no retention policy

D1 events and device registrations have no scheduled cleanup. A personal academic timeline and stale push tokens accumulate indefinitely.

**Fix:** document retention, add scheduled deletion of old acknowledged events and stale devices, preserve only metadata needed for recovery, and test cutoff behavior.

### M-13 — Stored transcripts are plaintext and can persist indefinitely

API credentials use secure storage, but transcript and summary JSON are plain SQLite. Cleanup occurs after success/ignored/duplicate; needs-review and terminal-failure payloads may remain forever.

**Fix:** disclose storage behavior, enforce retention for abandoned jobs, offer purge controls, apply restrictive file permissions, and evaluate encrypted SQLite with a key in OS secure storage. Do not sacrifice reliable resume without a replacement checkpoint design.

### M-14 — macOS/iOS compatibility is mostly scaffold-level

macOS release sandbox lacks `com.apple.security.network.client`; iOS has no Firebase configuration or background modes. CI builds neither platform. Current docs correctly avoid claiming full automation, but “compatible” is unverified.

**Fix:** add required macOS client/keychain entitlements, configure iOS only when product scope requires it, and add compile/smoke jobs on macOS. Keep feature capability tables explicit.

### M-15 — Release artifacts lack production trust controls

Windows installer is not Authenticode-signed. Android release silently falls back to debug signing when `key.properties` is absent (`apps/client/android/app/build.gradle.kts:53`). Release workflow builds artifacts without first running full Flutter/relay validation and publishes Windows/Android from separate jobs.

**Fix:** fail release builds without production signing, add Windows code signing, build AAB plus APK as needed, run validation before packaging, publish from one gated job, generate checksums/SBOM/provenance, and derive all versions from one source/tag.

### M-16 — CI hardening and coverage gates are missing

Workflows use movable action tags, broad release-job `contents: write`, no explicit concurrency, no coverage threshold, no dependency-update automation in-tree, no SAST/secret scan, and no artifact signing. Inno Setup is installed from an unpinned Chocolatey package during CI and release builds.

**Fix:** pin third-party actions by commit SHA, scope permissions per job, add concurrency cancellation, install tools deterministically, gate on handwritten coverage, add Dependabot/Renovate and CodeQL/secret scanning, and make tag release depend on CI success. Coordinate these with the separate GitHub-configuration task.

## Low-risk and quality findings

### L-01 — Relay accepts an unnecessary event type

Worker accepts `meeting.summarized` as well as `meeting.transcribed`, while normal setup subscribes only to transcript-ready. If both are configured, duplicate push wake-ups occur even though local Fireflies-ID dedupe prevents a second job. Restrict accepted events or document why both are needed.

### L-02 — Invalid persisted job status silently becomes `discovered`

`SyncJobStatus.fromWire` maps unknown values to `discovered`. Corruption or an incompatible migration can trigger reprocessing. Fail closed, log a schema error, and migrate explicitly.

### L-03 — External URLs are launched without scheme/host validation

Fireflies and Notion URLs are parsed and launched directly. Require HTTPS and expected hosts, then show safe failure for malformed remote data.

### L-04 — “Last sync” is a Fireflies discovery cursor

Tray reads the Fireflies cursor as “Last sync.” Cursor advances before job processing, so UI can show a recent sync while publishing failed. Store separate last-run start/end, discovery cursor, and outcome timestamps.

### L-05 — Class summary metadata is not populated

`AcademicSubject` has `summaryCount` and `latestSummaryTitle`, but cache mapping never derives them. Classes cards therefore show “No local summaries yet” even when jobs exist; class detail computes different local metrics. Use a database join/projection or remove misleading fields.

### L-06 — Diagnostics are too shallow for support

Export contains counts and mapping booleans but no redacted job timeline, app/schema version, last run outcomes, relay/polling health, or provider request IDs. Add bounded sanitized diagnostics and tests proving transcript/summary/token absence.

### L-07 — README key statement is technically inaccurate

README says no key is compiled into the app, while FlutterFire client configuration contains a Firebase API key. Firebase client API keys are public identifiers rather than service-account secrets, but wording can confuse secret review. Say “No private Fireflies, Gemini, Notion, relay, or Firebase service-account credential is compiled into the app,” and document Firebase API-key restrictions/App Check as external-console controls.

## Test and coverage plan

Priority order:

1. Queue lease/recovery tests for every persisted stage and concurrent coordinators.
2. D1 claim/per-device acknowledgement tests using Cloudflare's Worker Vitest pool and real migrations, not a SQL substring fake.
3. Notion adapter tests for block limits, ownership markers, templates, replacement safety, pagination, and response loss.
4. HTTP adapter tests for actual request shapes, auth placement, pagination, malformed bodies, provider codes, timeouts, 429, and both `Retry-After` formats.
5. Android tests for FCM-to-WorkManager handoff, lifecycle resume, process death, and notification preference.
6. Drift migration tests and retention/purge tests with prior schema fixtures.
7. Widget/accessibility tests for setup, subject review, failure recovery, narrow layouts, keyboard navigation, and screen-reader labels.
8. Packaging smoke tests for installed Windows launch/tray/uninstall/upgrade and signed Android release install/upgrade.

Measure handwritten source coverage separately from generated files and fail CI on regression. A first meaningful target is 80% for domain/database/integration adapters, with explicit branch coverage for state and error policies. UI percentage matters less than critical-flow widget coverage.

## Recommended delivery order

### Gate 1 — Data safety

Implement H-01 through H-07: local claims/recovery, D1 cross-device claim protocol, Notion-owned content markers, lossless block rendering, and phase-isolated sync. Amend ADRs and add failure-injection tests.

### Gate 2 — Unattended execution and security

Implement H-08/H-09 and M-01 through M-13: Android scheduling/foreground behavior, bounded resumable Gemini work, per-device relay auth, replay/rate limits, real connection validation, notification gating, retention, and encrypted-storage decision.

### Gate 3 — Release confidence

Close platform gaps, add real-boundary tests, enforce coverage, harden CI, require signing, test installers/upgrades, and validate live staging integrations with disposable Notion data before production use.

Production acceptance should be demonstrated with injected failure scenarios, not only happy-path mocks: kill processes at every checkpoint, run desktop/mobile concurrently, lose webhook/append responses, deny permissions, expire credentials, rate-limit providers, and verify exactly one intact Notion page survives.
